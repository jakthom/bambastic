# Access, user interfaces and network contracts

[Product specification](../PRODUCT-SPEC.md) · [OpenAPI contract](openapi.json) · [Bambastic MCP server](bambastic-overlay.md#first-party-mcp-server)

Bambuddy has human sessions, automation credentials, display links, third-party identity exchanges and LAN printer credentials. A wall display can show a machine's progress without disclosing the part name. A shop app can sign in a human and separately hold a key for submitting production. These distinctions belong in the server interface. [Access checks](../../bambuddy/backend/app/core/auth.py) · [Token scopes](../../bambuddy/backend/app/services/long_lived_tokens.py) · [Connected apps](https://wiki.bambuddy.cool/features/connected-apps/)

## Setup and identity lifecycle

- First use goes through the setup screen. The operator can complete setup with authentication disabled or enable it with a first administrator. On an existing installation the transition considers existing administrators and their credentials. Setup completion and the authentication flag are separate persisted facts. Enabling auth closes anonymous live connections. Switching modes has a migration path for the administrator's Bambu Cloud credentials. [Setup UI](../../bambuddy/frontend/src/pages/SetupPage.tsx) · [Authentication routes](../../bambuddy/backend/app/api/routes/auth.py)
- A local account has a username, password hash, active state, group memberships, optional email and user preferences. Create, edit, deactivate, change password and reset password are distinct operations. Protect the last active administrator. Deleting an account requires resolving ownership of affected records where the workflow asks for it. Changing groups, disabling an account, rotating a key or terminating a session must take effect for live connections as well as subsequent requests. [User management](../../bambuddy/backend/app/api/routes/users.py) · [User model](../../bambuddy/backend/app/models/user.py)
- With **advanced email authentication**, configure and test SMTP, provision accounts by email, deliver welcome/reset messages, and allow self-service password recovery. Personal print email preferences and administrative mail templates are separate from installation-wide event channels. A username/password sign-in yields a bearer session after any required second factor. Session policy defaults to 24 hours, with a configurable range of 1–720 hours for new sessions. Logout and password/security changes have revocation semantics. [Authentication](../../bambuddy/backend/app/api/routes/auth.py) · [Session policy](../../bambuddy/backend/app/core/auth.py) · [Operator guide](https://wiki.bambuddy.cool/features/authentication/)
- **Two-factor authentication** supports authenticator-app TOTP with enrollment confirmation and one-use recovery codes, and email OTP with a verified address and configured mail. Use an expiring pre-authentication challenge between password acceptance and second-factor success. Enrollment, regeneration, administrative reset and disabling are separate from login. Persist rate limiting, one-use state and revocation where a restart would otherwise reset them. Manage the key used for encrypted TOTP secrets and OIDC client secrets across restores. [Second-factor implementation](../../bambuddy/backend/app/api/routes/mfa.py) · [Encryption key resolution](../../bambuddy/backend/app/core/encryption.py)
- **LDAP** authenticates against a configured directory, supports search/provisioning, group mapping and default-group rules. Directory-backed passwords are managed by the directory. **OIDC** supports multiple providers, discovery, callback validation, optional linking/provisioning, configurable email and group claims, a default group on account creation, and optional automatic sign-in. Group sync replaces the groups managed by that provider and preserves separate manual assignments. An environment-managed provider is reconciled on startup and has read-only configuration in the UI. [LDAP](../../bambuddy/backend/app/services/ldap_service.py) · [OIDC routes](../../bambuddy/backend/app/api/routes/mfa.py) · [Group reconciliation](../../bambuddy/backend/app/services/oidc_group_sync.py) · [Environment provider](../../bambuddy/backend/app/core/oidc_env.py)
- When the server cannot confirm an existing session, the browser can show a reconnection state and retry. A transient network outage must not strand a signed-in kiosk on a login form. A confirmed expired/revoked session prompts authentication. [Browser session handling](../../bambuddy/frontend/src/contexts/AuthContext.tsx) · [Route guards](../../bambuddy/frontend/src/App.tsx)

## How authorization composes

| Question | Release rule |
| --- | --- |
| What action may this person take? | Permissions add across groups. System groups are Administrators, Operators and Viewers. Administrators have full authority. Default Operators can control devices and have ownership-scoped rights for many print assets. A custom group can grant selected actions such as clearing a bed, managing jobs, or reading finances. Settings visibility alone does not authorize a settings write. [Permission catalog and default grants](../../bambuddy/backend/app/core/permissions.py) |
| On which printers? | With auth off or an administrator, the fleet is unrestricted. For other users, take the union of all explicitly restricted groups' printer IDs and printers in their granted locations. Unrestricted groups make no contribution. Having zero restricted groups gives fleet-wide access. Having a restricted group with zero matches gives an empty printer set. Location membership changes as printers move. A printer outside scope returns 404 when accessed by ID. [Printer scope](../../bambuddy/backend/app/core/printer_scope.py) |
| Whose records? | Apply own/all permission to the creator and apply printer scope independently. Unbound rows have endpoint-specific rules, including pooled queue jobs. An archive that ran on an accessible printer can be visible even if its latest run was elsewhere. A destructive change to a shared archive requires scope over the whole affected archive. Project detail lists and exported files obey the caller's access. Whole-project production totals are shared. [Row visibility](../../bambuddy/backend/app/core/row_visibility.py) · [Archive scope](../../bambuddy/backend/app/services/archive_scope.py) · [Project reporting](assets-and-slicing.md#projects-and-production-targets) |
| Which folders? | An own-only reader can navigate their folders, shared folders, folders containing their files and required ancestors. Navigation through an ancestor grants no right to write there. Writing targets the root, an owned folder or a shared folder, subject to the operation's permission. Folder deletion accounts for descendants and trashed files. [Folder access](../../bambuddy/backend/app/services/library_folder_access.py) |
| Who can release production? | A creator lacking `queue:start_unreviewed` and `queue:update_all` gets a manual-start hold. A reviewer with authority over all queue jobs can release it, within printer scope. Permission to update one's own job alone cannot release a review-required job. Re-evaluate a pooled job against its creator's current device scope when choosing the printer. Restricted API keys must specify a printer for this operation. [Review policy](../../bambuddy/backend/app/core/auth.py) · [Queue API](../../bambuddy/backend/app/api/routes/print_queue.py) · [Target selection](../../bambuddy/backend/app/core/printer_scope.py) |
| Who pays? | Wallet ownership, cost-center membership and finance permissions govern the accounts available to a submitter. Queue and archive rights govern the source and execution. Creating a job can fail a budget check even for someone with permission to queue it. [Finance rules](materials-and-finance.md) |
| What about API keys? | The ordinary permission mapping starts from explicit capability flags, narrowed by the owner's authority. For device scope intersect the key allowlist and the owner's effective set. Null means all printers within that limit, an empty list means none. Removing a printer prunes its grant even when the list becomes empty. Newly owned keys and legacy ownerless keys have different cloud and ownership behavior. Dedicated capabilities for tariff updates and app messages expose their own narrow operations. [Key model](../../bambuddy/backend/app/models/api_key.py) · [Scope mapping and dedicated grants](../../bambuddy/backend/app/core/auth.py) |

For example, a viewer group plus a team restricted to Room A lets a user read the Room A printers. Granting operator permissions to the same user adds actions within Room A. A key limited to printer 8 belonging to that user can see printer 8 only while it is within the user's scope. A wall display, search result, aggregate count or asynchronous worker can expose the same data as a detail page, so each needs the corresponding scope check. [Scope tests](../../bambuddy/backend/tests/integration/test_printer_scope_1727.py) · [API key ownership tests](../../bambuddy/backend/tests/integration/test_api_key_owner_authority_1894.py)

## Interface compatibility

The supplied OpenAPI file contains **841 declared operations on 668 paths and 521 schemas**. Of those, **832 operations on 662 paths** are under `/api/v1`. It contains the tagged application's complete generated OpenAPI 3.1 definition, including per-operation descriptions, parameter and response schemas, defaults and declared status codes. Some responses are generic dictionaries or streams. Runtime errors, conditional access, callbacks and WebSockets require the accompanying behavioral contracts. For example, the two legacy direct-print handlers return 410 despite their generated success responses. [HTTP contract](openapi.json) · [Reference API](https://wiki.bambuddy.cool/reference/api/) · [Legacy route tests](../../bambuddy/backend/tests/integration/test_background_dispatch_api.py) · [Browser API client](../../bambuddy/frontend/src/api/client.ts)

| --- | --- |

The release also serves `/docs`, `/redoc`, `/openapi.json`, `/health`, the SPA entry and its PWA assets. Preserve per-endpoint casing, nullability, trailing slash aliases/redirects, streaming response types and download names for existing clients. Keys normally travel as `X-API-Key` or a bearer key. Supported capabilities include status, queue, control, library, archive, maintenance, inventory and project management. Cloud account reads are opt-in, owner-bound. [Key API](../../bambuddy/backend/app/api/routes/api_keys.py) · [API key guide](https://wiki.bambuddy.cool/features/api-keys/) |

### Example of asynchronous dispatch

A client submits a selected plate using `POST /api/v1/queue/`. This example stages plate 2 of archive 42 on printer 7 for manual release. The caller needs access to both the archive and the target.

```json
{"archive_id": 42, "printer_id": 7, "plate_id": 2, "quantity": 1, "manual_start": true}
```

The response identifies a stored queue item. The operator or reviewer can subsequently start that item. Upload progress carries `queue_item_id`, byte counts and a rounded percentage. `queue_item_acked` acknowledges the observed transition at the device, and a physical completion closes the run later. A request can succeed at the queue stage and then wait or fail at any subsequent stage. Connect actions to the returned ID. Verify each endpoint's concrete response shape in the schema and handler. [Create and start requests](../../bambuddy/backend/app/api/routes/print_queue.py) · [Dispatch notifications](../../bambuddy/backend/app/core/websocket.py) · [Queue contract](print-lifecycle.md)

### WebSocket and media access

- The browser obtains a short-lived socket token from `POST /api/v1/auth/ws-token` when auth is enabled, then connects to `/api/v1/ws`. The initial burst sends a `printer_status` snapshot for each visible device with cached state. Subsequent JSON messages include `type` and event-specific fields. For example, a printer update has `printer_id` and a nested `data` object, while transfer progress carries its fields at the top level. Client messages include `ping` (reply `pong`) and `get_status` for an allowed printer. [Socket endpoint](../../bambuddy/backend/app/api/routes/websocket.py)
- Live event families include printer state, start, completion, outcome requests, upload/ack/failure, plate check, spool assignments, usage and stock changes, kiosk scans/weights, billing failure, pipeline updates and announcements. Printer-bound broadcasts are scope-filtered. Some notifications target the initiating user. An archive update can be a minimal invalidation that causes the browser to reload the authorized view. Snapshot then subscribe/reconnect and refetch is the supported recovery pattern. This endpoint provides no durable event cursor or replay contract. [Server event envelopes](../../bambuddy/backend/app/core/websocket.py) · [Frontend consumers](../../bambuddy/frontend/src/hooks/useWebSocket.ts)
- Socket credentials expire after 60 minutes for admission. On a 4401 close, the client can recheck its session, obtain a new token and reconnect with backoff. Permission and scope changes can refresh or close open sockets. A client without the socket permission can still use permitted REST reads. [Socket credentials](../../bambuddy/backend/app/core/auth.py) · [Reconnect logic](../../bambuddy/frontend/src/hooks/useWebSocket.ts)
- Media embeds use purpose-bound credentials so that an image tag, OBS source or kiosk need not carry a browser login. The release has short-lived camera and media tokens, resource-bound slicer downloads, and named, revocable longer-lived camera tokens with a maximum lifetime of 365 days. `camera_stream` allows stream/snapshot, `camwall` adds a restricted fleet tile projection, and `overlay` adds overlay status including the current print name. The stream periodically rechecks access. [Long-lived scopes](../../bambuddy/backend/app/services/long_lived_tokens.py) · [Camera routes](../../bambuddy/backend/app/api/routes/camera.py) · [Wall projection](../../bambuddy/backend/app/api/routes/camwall.py)

The following message shapes cover the moments a replacement client must distinguish during a print. Each envelope carries its event name in `type`. [Socket publishers](../../bambuddy/backend/app/core/websocket.py) · [Browser event handlers](../../bambuddy/frontend/src/hooks/useWebSocket.ts)

| Event type | Wire fields and client interpretation |
| --- | --- |
| `printer_status`, `print_start`, `print_complete` | `printer_id` and a nested `data` object. The device and run context determine which screen or history entry to refresh. |
| `queue_item_uploading` | Top-level `queue_item_id`, `printer_id`, `printer_name`, `file_name`, `total_bytes`. Open progress for this dispatch. |
| `queue_item_upload_progress` | `queue_item_id`, `bytes_transferred`, `total_bytes`, `pct`. A value of 100 describes the file transfer. |
| `queue_item_acked`, `queue_item_failed` | Both identify the queue item and printer. An ack means the start watchdog observed a state transition. Failure includes `reason` and may have a null printer ID. |
| `archive_created`, `archive_updated` | Minimal invalidations. Visibility through an older run can yield an update with empty `data`. Refetch the authorized archive view. |
| `print_confirm_request` | `printer_id` and a nested `data` object. Offer the per-run verdict to eligible recipients. Applying that verdict is a separate write. |

### Client behavior on errors

Interpret status in the context of the operation. Typical cases are 401 for missing/expired authentication, 403 for insufficient authority, 404 for a missing or out-of-scope object, 409 for a state conflict or duplicate external batch reference, 422 for schema validation and 503 for a required unavailable service. Some domain checks return 400 with an explanation. An accepted slice job returns 202 and a trackable job. A pending print with a `waiting_reason` is a valid persisted result. A lost response to a submission that could start production needs reconciliation by job or external reference before a retry. ## Acceptance examples

1. A user with own-only library access sees their file under another folder's ancestor, can open the file and cannot upload a sibling into the navigation-only ancestor. Sharing a folder explicitly makes it an eligible upload target.
2. Assign a printer to another room while a restricted dashboard is open. Subsequent HTTP lists, wall data, statistics and device broadcasts reflect the new grant. A previously issued link follows its owner's current access.
3. Submit the same order batch twice with the same external source and reference after a simulated lost response. The second create reports a conflict. Looking up the existing batch lets the shop reconcile without submitting another physical job.
4. A connected app exchanges a valid consent code once, receives identity, and cannot reuse the code. Disabling Bambuddy authentication makes the app fall back to its own sign-in behavior.
5. Disconnect the browser from a local server during a print. The UI reports lost connectivity. On return it rebuilds from current state. Reopening a cached dashboard produces no new print command.
