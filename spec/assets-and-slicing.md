# Files, print history, projects and slicing

[Product specification](../PRODUCT-SPEC.md) · [Related print lifecycle](print-lifecycle.md)

A person can keep a design before they own a printer, prepare several plates from it, print one of those plates repeatedly, and discard the bulky files while keeping the production figures. These operations give the library file, archive and physical print different lifetimes. This chapter specifies the behavior of Bambuddy v.1.3.2. The section on rebuild seams proposes interfaces for implementing that behavior in another language.

## What each record represents

| Record | Identity and lifetime |
| --- | --- |
| Library file | An item in the user's file collection. It has a display filename, content type, storage location, owner and optionally a folder, tags, notes, photographs, thumbnail, import provenance and last print time. It can exist indefinitely without a print. |
| Print archive | A captured or uploaded print file, its parsed settings, plate estimates, user annotations, project, supporting design files and media. It can also be a record of an observed print whose file could not be retrieved. An archive can have zero, one or many runs on one or many printers. Some older archive fields mirror a run for display and compatibility. |
| Plate | One numbered arrangement in a 3MF project. Each plate can have different printable objects, thumbnails, filament slots, G-code, time and material estimates. A single archive can hold several plates. |
| Print log entry / run | One occurrence with its own printer, plate, start, finish, status, quality verdict, material, costs, duration and media. Queue item ID, archive ID and recorded user can be absent. Hardware-originated prints have no originating queue item. |
| Project | A grouping of work with linked files, archives, queue jobs and purchased parts. It can have a parent and production targets. The same file printed for a different project requires independent attribution. |
| Slice job / pipeline run | A slice job transforms a design into printable bytes. A pipeline run links one such transformation to one or more queue items and follows their outcomes. Only a physical print creates production history. |

The source defines these relationships and the fields retained for older data. [Library models](../../bambuddy/backend/app/models/library.py) · [Archive](../../bambuddy/backend/app/models/archive.py) · [Print log](../../bambuddy/backend/app/models/print_log.py) · [Project](../../bambuddy/backend/app/models/project.py) · [Pipeline run and copies](../../bambuddy/backend/app/models/pipeline_run.py)

## Library and asset storage

**Browse and organize.** The File Manager provides grid, list and keyboard-navigable column views, a folder tree, sorting, filters and deep links to selected folders or files. A folder search includes descendants while the query is populated. Clearing the query restores the immediate folder listing. Files occupy a single folder or the root. Tags are install-wide labels with case-insensitive, whitespace-trimmed uniqueness. Selecting multiple tags finds files with every selected tag across folders. Bulk add, remove and replace are distinct operations. Renaming a tag updates its uses. Folders can link to an archive or project and display a readable Markdown description, preferring a README or description file. [Library routes](../../bambuddy/backend/app/api/routes/library.py) · [Tags](../../bambuddy/backend/app/api/routes/library_tags.py) · [File Manager](https://wiki.bambuddy.cool/features/file-manager/)

**Folder access.** An own-files user can traverse their folders, folders shared with everyone, folders holding their files and the ancestors needed to reach them. A traversable ancestor alone grants no right to upload there. Only visible files contribute to its counts. Sharing a folder makes it available as a common destination while each file keeps its ownership. Deleting an owned subtree under own-delete permission requires ownership throughout, including trashed files. An ownerless legacy folder can be deleted under that permission when truly empty. External and project/archive-linked folders require broader deletion rights. [Folder access rules](../../bambuddy/backend/app/services/library_folder_access.py) · [Ownership tests](../../bambuddy/backend/tests/integration/test_library_folder_ownership_3201.py)

**Ingest and inspect.** Upload one or several files, download selections, rename, move, attach photos, add notes and external links, open a supported file in a desktop slicer or add printable items to the queue. ZIP import can recreate the internal directory structure and optionally create a parent named for the ZIP. Nested ZIPs stay individual files. A 3MF is a container. A project with embedded plate G-code is printable even when its filename is `model.3mf`. A geometry-only project named `model.gcode.3mf` needs slicing. Apply the same classification across upload, ZIP extraction and external scan. A missing preview should leave an otherwise accepted file usable. Ordinary upload can flag a byte-identical active file as a potential duplicate. Provider imports can return an existing copy. [Upload and classification](../../bambuddy/backend/app/api/routes/library.py) · [Misleading extension tests](../../bambuddy/backend/tests/integration/test_unsliced_named_gcode_3mf_3435.py) · [File browser](../../bambuddy/frontend/src/pages/FileManagerPage.tsx)

**Preview and assembly.** Show model geometry for STL/3MF and toolpaths for sliced output. A toolpath view allows plate and layer selection, camera rotation/zoom and coloring by feature or filament. Preview STEP geometry, PDFs, images and spreadsheets without changing the source. Oversized or unreadable previews fall back to download. For a plate assembled from several STLs, take an ordered selection with copy counts, combine repeated references to the same mesh, limit to 100 total instances, and create a new multi-object source 3MF. The originals stay individually usable. The operator can have the slicer arrange the combined plate. [Mesh combination](../../bambuddy/backend/app/services/mesh_combine.py) · [Toolpath viewer](../../bambuddy/frontend/src/components/GcodeToolpathViewer.tsx) · [Preview guide](https://wiki.bambuddy.cool/features/file-manager/)

**Storage ownership.** Managed files have internal disk names independent of their display names. An operator can register an allowed host directory, including a mounted share, with read-only and hidden-file options. A scan indexes its files and subfolders in place and uses filesystem modification times. Writable mounts support uploads and physical moves. Check the destination for readability/writability and collisions before moving data. Removing an external folder registration or deleting an indexed external file from the library removes Bambuddy's reference and derived data. The original external bytes remain on the host. A subsequent scan can rediscover them. [External scan and move operations](../../bambuddy/backend/app/api/routes/library.py) · [File Manager storage guide](https://wiki.bambuddy.cool/features/file-manager/)

**Retention.** Deleting a managed *file* moves it into recoverable trash. The default retention is 30 days, adjustable between 1 and 365. The trash supports scoped listing, restore, permanent removal and emptying. Managed *folder* deletion cascades through the subtree, including trashed contents. A separate age-based cleanup previews counts and size, excludes external files, and sends eligible managed files to trash. The criterion is last printed time, optionally upload time for never-printed files. Its automatic mode defaults off with a 90-day age threshold. When a file is permanently removed, cancel still-pending/skipped queue items that depend solely on it, with an explanation. Detach remaining references so an underway print and finished batch history survive. [Trash lifecycle](../../bambuddy/backend/app/services/library_trash.py) · [Folder deletion](../../bambuddy/backend/app/api/routes/library.py) · [Trash tests](../../bambuddy/backend/tests/integration/test_library_trash_api.py)

**Variants.** A reusable group associates peer printable files for different target printer models. Require distinct files, one per normalized model, in at most one group each. A missing model can be supplied explicitly and kept separately from parsed metadata. Member order establishes preference. Removing a member dissolves a group that has fewer than two remaining members. Ungrouping preserves each file. A selection can create separate queue jobs or a single alternatives job that prints the matching member once on an eligible machine. Combining STLs produces geometry for one plate and has different semantics. [Variant groups](../../bambuddy/backend/app/api/routes/library_variants.py) · [Queue variants tests](../../bambuddy/backend/tests/integration/test_queue_variants_api.py)

## Archive, runs and media

**Capture and browse.** Archive a print observed on a printer, a Bambuddy dispatch or a slicer submission, or explicitly upload one or more 3MFs. Automatic capture of external jobs honors both the install and printer settings and skips printer-internal calibration work. Display a file card with the latest applicable run, printability, plate thumbnails, slice target, settings, consumption, estimate and outcome. Users can open a stable archive URL, switch between grid/list/calendar, filter favorites, duplicates, never-printed or failed work, tag or edit records in bulk, and reopen an original or sliced file. The calendar places each run on the local day it ended. Uploading an unprinted design contributes zero runs to that calendar. Editing notes, tags, quantity, failure reason, links and favorite status provides context that subsequent prints must preserve. [Archive behavior](../../bambuddy/backend/app/api/routes/archives.py) · [Archive workspace](../../bambuddy/frontend/src/pages/ArchivesPage.tsx) · [Archiving guide](https://wiki.bambuddy.cool/features/archiving/)

**Reuse and merge have different predicates.** For library/queue dispatch, reuse an archive with the same file content, owner and project when its library file is the same or its library association is absent. A new print of another plate still produces its own run. For an unowned slicer/printer-originated job, identical plate G-code can identify the previous slice despite new outer 3MF bytes. This route targets an unowned, unprojected archive without a library association. Preserve user naming, annotations and media when replacing its bytes. When replacing would interfere with another active use, append the run and retain the current file. Changed G-code is new work. For older duplicates, preview groups by whole-file hash, owner and project. Merging into the oldest archive combines runs, photos, videos, notes, tags and dependent references. Historical IDs resolve through aliases and financial bookings keep their original attribution. Busy archives, prints ended within the media-collection window of 30 minutes, and conflicting original source/design attachments are reasons to skip. [Slicer resend cases](../../bambuddy/backend/tests/integration/test_slicer_resend_joins_archive_1634.py) · [Merge rules](../../bambuddy/backend/app/services/archive_merge.py) · [Operator behavior](https://wiki.bambuddy.cool/features/archiving/)

**Run history and corrections.** An open run can be written at start and completed in place. History and statistics normally exclude open rows, while active-print surfaces and archive export can include them explicitly. Repeated reports for the same occurrence must converge. A run carries its own printer, plate, timing, media, quantities where recorded, charge identity and outcome. Editing an archive's displayed outcome mirrors it to the latest run. Editing an older run can correct its classification or notes without replacing the latest run. Machine completion and the operator's good/reject decision are independent. A manual correction of archived grams repairs Bambuddy's accounting view without issuing a second inventory consumption operation. The global Print Log supports filters, server-side sort/pagination, optional columns, per-row edits/deletes and clearing within the permitted scope. Clearing the log affects derived measurements and preserves archive files and queue entries. [Run reconciliation](../../bambuddy/backend/app/services/print_log.py) · [Log operations](../../bambuddy/backend/app/api/routes/print_log.py) · [Print Log guide](https://wiki.bambuddy.cool/features/print-log/)

**Visibility follows runs.** An archive that printed on A and B can be visible to an A-only operator. Show that person's permitted run, outcome, costs, finish photos and video, including in calendar, download and export. Mutations affecting the complete shared archive require scope over all its printers in addition to the applicable ownership right. A printer's last print can refer to this shared archive even when the archive's most recent run was on another machine. [Archive scope](../../bambuddy/backend/app/services/archive_scope.py) · [Per-run visibility tests](../../bambuddy/backend/tests/integration/test_archive_scope_per_run.py)

**Media and design lineage.** Keep file-level manual photographs, a source 3MF, an optional Fusion 360 design file, designer attribution, external URL and the 3MF's embedded project description and images. Present per-run finish photos and videos alongside the relevant print. A saved listing of the printer's timelapse directory at print start helps match newly written videos even when printer clocks drift. Offer scan, ambiguous-candidate selection, manual upload, download and removal. The editor supports trim, speed and audio. It runs one background transcode per archive and exposes progress, cancellation and result after the editor closes. Missing media degrades to the available file, thumbnail or history. [Archive and media fields](../../bambuddy/backend/app/models/archive.py) · [Media operations](../../bambuddy/backend/app/api/routes/archives.py) · [Transcode jobs](../../bambuddy/backend/app/services/timelapse_jobs.py)

**Delete and purge.** Before deleting an archive show the number of linked queue entries. An actively printing linked queue item blocks the operation with a conflict. Default archive deletion removes physical files, hides the archive and removes linked queue items. Its log and global statistics survive. The explicit remove-from-statistics choice deletes the runs as well. Deleted archives cease to contribute to project-specific figures. An optional archive age policy previews count, size and sample names, measures age from completion, then start, then creation when earlier values are unavailable, and defaults to 365 days when enabled. A recent reprint refreshes its eligibility. The library trash retention window applies to library files. [Archive delete](../../bambuddy/backend/app/api/routes/archives.py) · [Archive purge](../../bambuddy/backend/app/services/archive_purge.py) · [Project membership and counts](../../bambuddy/backend/app/api/routes/projects.py)

**Search and comparison.** The archive search endpoint accepts at least two characters, includes print name, filename, tags, notes, designer and filament type, and accepts printer/project/status filters. SQLite FTS5 and PostgreSQL text search have different token/operator semantics and a case-insensitive substring fallback handles index failures. Test prefix queries and permissions on each supported database. The wiki's search syntax examples extend beyond the portable subset. Compare two to five accessible archives in selection order. The server returns raw/formatted values, units, a difference flag, and simple associations between settings and successful or failed examples. This release compares layer height, nozzle diameter, bed and nozzle temperature, filament type/weight, estimated time, layers and status. Missing measurements stay unknown. [Search and comparison routes](../../bambuddy/backend/app/api/routes/archives.py) · [Comparison fields](../../bambuddy/backend/app/services/archive_comparison.py) · [Search guide](https://wiki.bambuddy.cool/features/search/) · [Comparison guide](https://wiki.bambuddy.cool/features/comparison/)

## Projects and production targets

A project has a name, description, color, optional URL/cover, rich notes, attachments, tags, due date, priority, budget and status (`active`, `completed`, `archived`). Users link archives and queue jobs individually or in bulk, print or queue from linked library folders, review timeline events, and manage a bill of materials. Each purchased item tracks quantity required and acquired, unit price, sourcing link, remarks and optional file/archive references. BOM estimated cost uses unit price times quantity required. Project cost combines recorded filament, energy, wear and BOM. Templates carry reusable planning data and a fresh project's acquisition starts over. A project label can identify the work outside the application. [Project model](../../bambuddy/backend/app/models/project.py) · [Project operations and templates](../../bambuddy/backend/app/api/routes/projects.py) · [Projects guide](https://wiki.bambuddy.cool/features/projects/)

| Operator question | v.1.3.2 calculation |
| --- | --- |
| How many plates have we run? | Project totals count ended run rows joined to live member archives. The plates progress ratio divides that run count by the plates target. The wire field named `total_archives` carries the run count. A repeat contributes another run. |
| How many usable parts do we have? | Sum the archive's part quantity for each completed, unrejected run. The archive parser can infer quantity from objects on the plate and the user can correct it. A completed run with a `reject` verdict yields zero usable parts. |
| How many complete sets can we assemble? | Count completed unrejected runs per printable linked file. Attribute using the library file ID, then content hash, then filename for legacy rows. Complete sets are the minimum count across those files, including zero for an unprinted file. With counts 4, 4 and 1 there is one complete set. |
| Does this include the sub-projects? | The detail view provides a project's own totals and, for a parent, a second roll-up over descendants and summed targets. Parents cannot form cycles. Deleting an intermediate project reattaches its children to its parent, detaches its prints, and removes its own BOM. |

Projects are shared planning records. Detailed archive/queue lists, timeline items and linked files obey the caller's corresponding permissions. Project aggregate production figures are shared. ZIP export packages the project manifest, BOM and accessible files/thumbnails from linked folders. JSON carries metadata and folder/file descriptions. Treat project transfer separately from historical print export and full installation restore. [Totals, per-file fallback and export](../../bambuddy/backend/app/api/routes/projects.py) · [Complete-set display](../../bambuddy/frontend/src/pages/ProjectDetailPage.tsx)

## Server-side slicing

1. **Choose the source and plate.** The direct library slice accepts STL or 3MF. STEP can be stored and previewed and must be converted before direct slicing. If the source has multiple plates, choose a one-based plate index. Omitted means plate 1. Explicit 0 means all plates in one output container. Determine per-plate filament requirements from existing slice metadata where available. For an unsliced project, preview slicing can recover them, with painted-face data as a fallback. Cache preview results by source identity, plate and content fingerprint. [Slice request](../../bambuddy/backend/app/schemas/slicer.py) · [Preview cache](../../bambuddy/backend/app/services/slice_preview.py) · [Library slice](../../bambuddy/backend/app/api/routes/library.py)
2. **Resolve the recipe.** Choose printer, process, ordered filament preset references and optionally bed type and per-slot colors. Accept legacy numeric local-preset IDs and single-filament requests. Preserve empty color positions in the array so a missing first color does not shift the second. Unused project slots may need placeholders when slicing one plate. Supply that plate's lowest used slot's profile in their positions so unused materials cannot introduce unrelated compatibility checks. Bed names follow the selected engine, with aliases for older saved requests. [Request validation](../../bambuddy/backend/app/schemas/slicer.py) · [Resolution and routing](../../bambuddy/backend/app/api/routes/library.py)
3. **Choose whose design settings to use.** The ordinary path starts with the selected profiles, carries applicable support settings, then selected changes from the design, then the user's explicit process edits. Empty selected design keys and omitted selections are different for older clients. Alternatively, the UI offers the entire embedded configuration for a 3MF designed for the selected printer. Respect authored positions/orientations by default. A cross-class conversion between single- and dual-nozzle layouts forces arranging on the new build surface. The actual target model goes on the resulting file. [Process settings](../../bambuddy/backend/app/services/process_overrides.py) · [3MF conversion](../../bambuddy/backend/app/services/slicer_3mf_convert.py) · [Slice guide](https://wiki.bambuddy.cool/features/slicer-api/)
4. **Run the external engine.** Bambuddy selects a headless OrcaSlicer or Bambu Studio HTTP sidecar according to its configuration. The repository supplies integration and Compose definitions for separately built images. Native deployment described for these images is Linux amd64, with an experimental emulated ARM64 deployment. `POST /api/v1/library/files/{id}/slice` or `/api/v1/archives/{id}/slice` returns 202 and an ID with a polling URL. The process-local job progresses from `pending` to `running`, then `completed` or `failed`. A finished job becomes eligible for eviction after 30 minutes. The client can close the dialog and follow progress elsewhere. An expired or inaccessible job returns 404. Preserve reported progress, absence of progress for older engines, and diagnostics for rejected inputs, oversized uploads, sidecar unavailability and stalls. The stall timeout measures silence while valid progress permits a longer slice. [Sidecar distribution](../../bambuddy/slicer-api/README.md) · [Engine client](../../bambuddy/backend/app/services/slicer_api.py) · [Job store](../../bambuddy/backend/app/services/slice_dispatch.py) · [Polling](../../bambuddy/backend/app/api/routes/slice_jobs.py)
5. **Validate and save.** The engine's successful HTTP response alone is insufficient. Validate printable output. Reject an invalid 3MF response. When the engine used a Standard printer preset, a recognizable omission of its Bambu start program fails the job before publication. A detectable unresolved filament profile can produce plausible default temperatures. This version logs a warning identifying the slot and keeps the result. A content rejection surfaces the slicer's reason. A compatible 3MF can recover from a profile-path engine failure with an embedded-settings retry when source and target models are both known and equal. Do not accept that fallback for a different or unknown target, or where it would collapse the arranged plates. Return whether embedded settings were used. Fill missing plate thumbnails where possible. Long-running operations must recheck ownership when publishing a result if the initiating user was deleted. [Output checks](../../bambuddy/backend/app/services/slice_output_check.py) · [Output persistence and provenance](../../bambuddy/backend/app/api/routes/library.py)

## Saved pipelines and copy outcomes

A pipeline is a named printer/process/filament(s)/bed recipe with a dispatch target and distribution strategy. Define one from Settings or save current choices in the Slice dialog. Pipeline read, write and run are distinct permissions. Removing the definition hides it and preserves run history. Starting a run takes exactly one source, either a library file or an archive the caller may reprint. Default copies is one, the default configured ceiling is 50, and the request schema caps copies at 1,000. A run records creator, input, generated file, copy indices, assigned printer and queue references. [Pipeline definitions](../../bambuddy/backend/app/api/routes/slicer_pipelines.py) · [Run schema](../../bambuddy/backend/app/schemas/pipeline_run.py) · [Runs dashboard guide](https://wiki.bambuddy.cool/features/slicer-pipelines/)

**Eligibility and dispatch.** Preview a per-printer report covering configured target, activation, connection, expected slots, verifiable material and color. A class passes when any candidate passes. A recipe using a filament whose identity cannot be established locally reports an informational unverified result. A blocking result returns 409 with the same report unless the operator explicitly forces it. Store the override on the run. A usable target, source access and printer scope still apply. Slice once, then create the copies with the initiating user's attribution, install defaults and required job-review flags. A specific target pins every copy. For a class, `max_parallel` leaves selection to the scheduler, `fill_one_first` pins all copies to the first matching active in-scope printer ordered by ID, and `round_robin` cycles over that ordered set. The two pinning strategies use the configured matching fleet and can wait on their chosen printer. [Eligibility](../../bambuddy/backend/app/services/pipeline_eligibility.py) · [Assignment, cancellation and enqueue rules](../../bambuddy/backend/app/api/routes/pipeline_runs.py)

**Observing the result.** Runs move through queued, slicing, dispatching and in-progress stages as applicable. A slice failure creates no dispatch. A cancellation received while slicing is checked before enqueue. A late result can exist as a library file even when the user canceled the run. Canceling pending work is distinct from issuing a hardware stop to a running printer. Per-copy outcomes determine completed, cancelled, failed or partial failure. If an older queued/printing copy lost its queue record without a recorded final state, its outcome is unknown. The roll-up treats unknown as ended and retry excludes it. Retry creates a new, parent-linked run for exactly the failed/cancelled copies. Clear-history acts on terminal runs in the caller's mutation scope. The UI can filter runs and expand them down to individual copies. ## Statistics, quality and exports

The dashboard provides quick totals, success, time accuracy, failure analysis, activity, records, printer comparisons and material trends. Users can resize, hide or reorder widgets, reset the layout, and select preset or custom calendar dates. Layout and time range persist in the browser. The user filter is a separate permission and includes unattributed/system runs. Supplier and material-number widgets require internal inventory mode. Preserve the distinction between run material cost, measured electricity cost and configured hourly printer wear when showing totals. Pricing and inventory supply those facts. [Dashboard](../../bambuddy/frontend/src/pages/StatsPage.tsx) · [Statistics schema](../../bambuddy/backend/app/schemas/archive.py) · [Statistics guide](https://wiki.bambuddy.cool/features/statistics/)

| Measurement | Definition and edge cases |
| --- | --- |
| Print count and success | Count ended log entries, including a fresh entry for every reprint. The quality-outcome denominator is completed + failed + aborted. Completed divided by that denominator gives machine success. Stopped, cancelled and skipped are shown separately. Removing files under normal archive deletion preserves historical counts. |
| Yield | In failure analysis the numerator is completed minus operator-rejected completed runs. Use the same quality-outcome denominator. A completed part can lower yield while machine success stays constant. Show failure and rejection reasons separately. Breakdowns include reason, filament, printer, hour, recent failures and weekly trend. |
| Time and accuracy | Prefer measured duration. When time is unknown the total-time calculation has source estimates as a fallback. For accuracy use completed runs with measured timing and an estimate. Divide estimated seconds by actual seconds and multiply by 100. Use the printed plate's estimate when known. The aggregate omits values below 50% or above 200%. An unmeasured or missing sample yields an absent accuracy value. |
| Energy | Total-consumption mode uses the plugs' lifetime counters for all-time and counter snapshots for a date range. Sparse snapshot history has a warming-up state. Print-only mode aggregates the runs' measured energy. The two figures answer different questions about idle power. |
| Dates and printers | A calendar date is interpreted in the requested IANA time zone (server default if omitted). History aggregates filter log event time, the archive calendar groups when runs ended, and archive export's date filter selects when runs started. Keep printer names recorded with historical runs so deleting a device does not erase its label. |

These formulas are observable in the aggregation paths. For example, six completed runs, one of them rejected, two failed runs and two cancellations yield ten ended entries, 75% machine success and 62.5% yield. [Statistics calculations](../../bambuddy/backend/app/api/routes/archives.py) · [Failure analysis](../../bambuddy/backend/app/services/failure_analysis.py) · [Plate-specific comparison tests](../../bambuddy/backend/tests/integration/test_plate_estimates_3375.py)

**File exports.** CSV and XLSX archive exports combine repeated file fields with each visible print's own plate, printer, start/end, material, outcome, energy and costs. An unprinted archive contributes a file row with empty print columns. An older archive with a recorded print and no separate run can supply its historical fields. Search/project filter files. Printer/status/date filter individual prints. The failed collection includes aborted runs. End-of-day boundaries are inclusive, and multi-printer privacy applies to each exported run. An ordinary archive export omits soft-deleted files, including ones still counted by Quick Stats. Statistics export is a different report, with failure counts, breakdowns and trend by period. In this release the dashboard's export button requests 90 days and the selected user, even when the dashboard uses a custom period. The report API exposes a day count. ## Rebuild seams

These are proposed module interfaces. They can run in one process. Their contracts follow the lifecycle and permissions described above.

| Module | Inputs and outputs | Behavior worth keeping inside |
| --- | --- | --- |
| Asset library | Store, inspect, list, move, trash or restore a file identified by stable ID. Return storage disposition, readable metadata and effective operations for that caller. | Managed storage and mounted-directory adapters implement different deletion and move behavior. Case-normalized tags, scope, thumbnails, deep links and saved variant membership use the same file identity. |
| Archive and history | Capture artifact, associate or merge file, open/finish run, record verdict, list visible runs, attach media. | Reuse rules, duplicate reports, concurrent printer runs, aliases, media ownership, and the latest-run projection are consistent across dashboards and exports. |
| Preset catalog and model sources | Resolve source-specific references in caller context. Import model/instance or selected file into a writable destination and return existing/new state. | MakerWorld and Manyfold differ on credentials, discovery and download type. Source descriptors and preset IDs survive display-name collisions and upstream version changes. |
| Slice execution | Accept source bytes/reference, plate, ordered presets, overrides and intended output destination. Return an asynchronous job, validation outcome and output file/archive ID. | The engine can be replaced without spreading vendor profile resolution, 3MF parsing and cross-model fallback through UI, scheduler and importer code. Progress and valid output are independent signals. |
| Pipeline orchestration | Bind recipe, authorized source, target and copies into one run. Emit copy-level queue requests, observe queue outcomes, cancel and retry eligible copies. | One slice can feed many copies. Persist per-copy identity and terminal outcome so retry never depends on inferring how many jobs a shared archive printed. |
| Project reporting | Attach/detach members, set planning targets, derive visible detail and shared aggregates. | Calculate plates, good parts, sets and BOM against their respective units. Keep whole-project totals separate from global run statistics and local-day export filters. |
